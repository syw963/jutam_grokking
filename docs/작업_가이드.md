## GPU 서버

- RunPod, RTX 4090 24GB, CPU 48코어. VS Code SSH로 접속.
- 모델이 작아서 run 하나는 GPU를 거의 못 쓴다. **묶음 학습(`sweep.py --multi`)으로 여러 run을 한 프로세스에서 돌린다.**
- 묶음 하나는 약 3GB(`--rows-budget` 기본 16384). 동시 묶음 수 `--jobs`는 5~6이 안전하다. 7개 이상이면 메모리 부족(OOM).
- B200 같은 큰 GPU로 바꿔도 run 하나의 속도는 거의 그대로다. 묶음 크기를 키우거나 서버 수를 늘려야 빨라진다.
- 측정값(E5, 묶음 4개 동시, 묶음당 24 run): 1,000 step에 train 256개 23초, 1,024개 103초, 4,096개 415초. train 크기에 거의 비례 → 계산량이 시간을 정한다. 전력 317W/450W.
- 대칭 위반 점수는 `--sym-every`(기본 1,000 step)마다만 잰다. 그 사이 평가의 sym 열은 빈 값(nan)이다.
- **GPU가 한 개뿐인 서버에서 `CUDA_VISIBLE_DEVICES=1`을 쓰면 GPU를 못 찾는다.** 예전 코드는 이때 조용히 CPU로 돌았다(E6 첫 시도 30분 낭비). 지금은 오류로 멈춘다. `nvidia-smi`로 GPU 번호를 먼저 확인한다.
- GPU를 하나 더 쓸 때: 같은 서버에 GPU가 두 개 보이면 `CUDA_VISIBLE_DEVICES=1`을 앞에 붙이고, sweep이 도는 폴더가 아닌 **다른 폴더에 clone**해서 돌린다. 새 서버면 clone → `pip install -r requirements.txt` → 실험 스크립트. 데이터는 seed가 고정이라 새로 만들어도 같다.

## GPU 여러 개로 나눠 돌리기

- **한 서버에 GPU 여러 개(권장)**: `GPUS=all JOBS=2 GROUP=20 bash experiments/<실험>.sh`
  - `sweep.py --gpus all`이 묶음마다 GPU를 하나씩 배정한다(`CUDA_VISIBLE_DEVICES` 자동). `--jobs`는 GPU 하나당 동시 묶음 수.
  - `GROUP`(묶음당 run 수)을 줄이면 묶음 수가 늘어 GPU를 고르게 채운다. 묶음 수 ≈ GPU 수 × JOBS가 되게 잡는다.
- **서버 여러 대**: 각 서버에서 `SHARD=0/3`, `SHARD=1/3`, `SHARD=2/3`처럼 실행. 작업 목록을 나눠 맡는다. 결과 tgz를 서버마다 받아 합친다.
- 4090 한 장은 묶음 5개(묶음당 65 run)로 전력 346W/450W까지 찼다 → 거의 포화. GPU를 늘리면 거의 비례해서 빨라진다.

4. 멈출 때는 `pkill -f sweep.py; pkill -f train_multi.py; pkill -f train.py` 후 `ps aux | grep -E "sweep|train" | grep -v grep`으로 확인.
5. 같은 sweep을 두 번 띄우지 않는다(같은 run 폴더에 겹쳐 씀). 다시 띄우기 전에 반드시 멈춘다.
6. 끊긴 sweep은 같은 명령으로 다시 실행하면 이어서 돈다(끝난 run 건너뜀, 5,000 step 체크포인트부터 재개).

### GPU 배분 (10월 20일 2시 개선)

- `sweep.py`는 이제 **같은 서버의 모든 sweep을 통틀어 가장 한가한 GPU**에 묶음을 배정한다(`/tmp/jutam_gpu_load.json`, 파일 잠금).
  예전에는 sweep마다 GPU 0부터 채워서, sweep 여러 개를 동시에 띄우면 GPU 0에 몰리고 마지막 GPU가 놀았다.
- 묶음은 **계산량이 큰 것부터** 시작한다(train 행 수 × run 수 × 모델 크기 × 최대 step). 긴 묶음이 마지막에 혼자 남는 것을 줄인다.
- 그래도 남는 불균형: 일반화하지 못하는 묶음은 최대 step까지 돌아서 미리 알 수 없다. 묶음 크기를 작게(`--group-size`) 하면 덜하다.

## 자주 쓰는 확인 명령

진행 상황 (규칙 × train 크기 × seed):

```bash
cd /workspace/jutam_new
python - <<'EOF'
import csv, glob, json, os
from collections import defaultdict
RUNS = "runs_boundary"   # 확인할 run 폴더
tab = defaultdict(list)
for d in glob.glob(f"{RUNS}/*/"):
    if not os.path.exists(d + "summary.json"): continue
    s = json.load(open(d + "summary.json"))
    rows = list(csv.DictReader(open(d + "metrics.csv")))
    te = float(rows[-1]["test_exact"]) if rows else 0
    tab[(s["rule_name"], s["train_sets"])].append((s["seed"], s["last_step"], te, s["t_fit"], s["t_gen"]))
for (r, c), v in sorted(tab.items()):
    cells = "  ".join(f"s{sd}:{st//1000}k {te:.2f} fit={tf} gen={tg}" for sd, st, te, tf, tg in sorted(v))
    print(f"{r:18s} tr{c:<5} {cells}")
EOF
```

## 확정된 학습 설정

- lr **3e-4** (1e-3은 학습이 무너짐. bf16·grad clip은 원인 아님)
- AdamW betas (0.9, 0.98), weight decay 1.0, warmup 100, 고정 학습률, full batch
- 모델 m0: 2층, d=128, head 4
- 판정: t_fit = train exact ≥ 0.99, t_gen = test exact ≥ 0.95. 지연 = t_gen − t_fit
- 데이터: n=50, m=5, 값 집합 단위 split, test 20,000, 순서 고정. train은 **개수**로 정한다(비율 아님)

## 서버 자동화 (10월 22일 정리, 실수에서 배운 것)

- **결과 자동 업로드 + 서버 멈춤:** 서버에 GitHub 토큰(fine-grained, 이 저장소 쓰기, 7일)을 넣어 클론하고, 실험 스크립트의 PID를 기다리는 대기 프로그램을 띄운다:
  `P=$! ; P=$P nohup bash -c 'while kill -0 $P 2>/dev/null; do sleep 60; done; ... git push; runpodctl stop pod $RUNPOD_POD_ID' &`
  - **스크립트 이름으로 기다리면 안 된다**(`pgrep -f 이름`): 대기 프로그램 명령 안에 같은 이름이 들어가면 자기 자신을 찾아 영원히 기다린다(10월 22일 새벽 E32·E33 업로드·멈춤 실패 원인).
  - 서버의 runpodctl은 옛 버전: **`runpodctl stop pod <ID>`**가 맞다. `runpodctl pod stop`은 도움말만 띄우고 성공으로 끝나서 대체 명령이 실행되지 않는다(E30 서버 안 멈춘 원인). 시작할 때 `runpodctl get pod`로 권한부터 확인.
- **GPU 메모리:** 학습 프로세스 하나가 약 1.5~3GB. 스크립트마다 sweep이 여러 개 동시에 떠서 JOBS만으로는 총 개수가 제한되지 않는다 → 환경변수 **`JUTAM_MAX_PER_GPU=k`**로 서버 전체 GPU당 동시 학습 수를 제한(24GB → 5, 32GB → 6).
- 결과 tgz는 저장소 `results/`에 모은다(E30_noise, E31_gpt_law, E32_big_law, E33_mul_law, E35_mul_structure, *_partial은 1차 실행 백업).
